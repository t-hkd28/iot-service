# 担当分担案と完成条件（指導者とチームで調整）

| 担当 | 主な実装対象 | 完成条件 |
|---|---|---|
| A：MQTT・非同期処理 | `MqttReceiver` | ブローカー接続、購読、受信JSONをExecutorへ渡し、別スレッドでServiceを呼ぶ |
| B：Repository・DB | `AbstractSensorDataRepository`、`JdbcSensorDataRepository` | 入力検証、INSERT、最新順SELECT、例外処理、リソース解放 |
| C：サービス・保存方式切替 | `SensorDataService`、`RepositoryProducer` | JSON変換、Repository委譲、JDBC/CSV切替 |
| D：REST API | `SensorResource` | limit検証、200/400応答、JSON返却。curlで確認できる |
| E：Web画面 | `index.html`、CSS、JS | 件数指定、更新、一覧表示、空・通信エラー表示 |

## 配布時点で実装済みの部分
- `SensorData`、`SensorType`、`StorageType`
- `SensorDataRepository`
- `CsvSensorDataRepository`（CSV保存・取得の完成版）
- `SensorPipeline`（Quarkus起動・終了イベントとの接続）

JDBC Repository、MQTT受信、Service、REST API、Web画面は訓練生が実装します。CSV RepositoryはJDBC Repositoryの完成を待たずに利用できるため、先にCSV方式でService・REST API等の結合確認を行い、その後JDBC方式を実装します。

## 全員で確認する共通仕様
- `SensorData`の項目名・型を変更する場合は、MQTT送信側・DB・API・画面の担当者全員で合意する。
- API：`GET /api/sensors?limit=100`。limitの有効範囲は1～1000。
- 正常応答はJSON配列。範囲外のlimitはHTTP 400。
- MQTT JSONはREADMEのサンプルに従う。
- MQTT受信コールバック内でDB/CSVアクセスを直接行わない。Executorに処理を渡す。
- 保存方式は`APP_STORAGE_TYPE=CSV`または`JDBC`で切り替える。

## チーム開発上の約束
- 指導員が用意したGitHubリポジトリを全員が`git clone`して使用する。訓練生が新規リポジトリを作成したり、`git init`したりしない。
- `main`へ直接pushしない。作業ブランチを作り、Pull Requestで統合する。
- 1つのPRで扱う変更を小さくする。
- クラスやメソッドのシグネチャを変更するときは、先にチームへ共有する。
- 高速に進められるメンバーが他の担当の実装をすべて肩代わりしない。レビューと相談支援に留める。
- 作業が止まったら、試したこと・エラー内容・次に確認したいことを記録して相談する。
